### 2.4 Chat Assistant (`/chat`)

Once a conversation starts, the input placeholder changes to "Type your next question…". Messages render as chat bubbles (user messages right-aligned, green; assistant messages left-aligned with a small bot icon, streamed/markdown-formatted with bold text and bullet lists). Observed exchange: user asked "What should I focus on for skin quality?" → assistant answered with a structured "Skin quality — key focus" response citing the user's own actual measured skin condition ("good condition with a smooth texture and a medium skin tone") and gave a morning/evening routine. ## 3. What the PDF Shows

The 16-page "Protocol" PDF export is the same underlying report as the interactive `/report` screen's static/printable form. Structurally it is **already very close to this project's existing Phase 1 report** (`docs/report_design_spec.md` / `docs/report_template.md` / `FR-009`–`FR-014`):

- Cover/overview page (score, evaluated points, analysis time, priority-features-to-improve callouts, before/potential image pair, facial age, harmony radar chart, overview paragraph, feature-evaluation table, treatment-protocol phases).
- Disclaimer/Privacy Policy page (informational-only framing, no medical-advice claims, 30-day offline content retention note, consent language) — substantively matches this project's existing disclaimer content and `FR-004`'s BDD-safety intent.
- Introduction page (cephalometric-measurement framing, limitations note, table of contents).
- "Understanding the Results" page — four numbered principles ("MyFace does not rate attractiveness," "recommendations are informational and aesthetic purposes only," etc.).
- Protocol overview page (before/after image, **explicitly states "This report is organised around 11 key features"**, then lists exactly: Hair, Eyebrows, Eyes, Nose, Cheeks, Jaw, Lip, Chin, Skin, Neck, Ear).
- **One page per feature** — Hair, Eye (combines Eyebrows/Eyelashes/Eyes/Under-eye into one page), Nose, Cheek, Jaw, Lip, Chin, Skin, Neck, Ear. Each page: a narrative "Recommendations" section citing specific measured attributes by name (e.g. "Full hairline, Low forehead exposure, Straight texture"), a before/after image slot, a "Recommendation tier" label (Non-invasive/OTC, matching `FR-012`'s tiering), and a short "\[Feature\] Summary" closing paragraph.
- Closing Recommendations page — a synthesized, cross-feature narrative plus a prioritized action list.

**Key finding: the PDF's page list is exactly the current 11 features (no "Smile" page)** — confirming the PDF/print export and the interactive `/report` screen's "Features Analysis" nav (§2.2 above, which does include Smile) are not perfectly 1:1 in this reference product either. This supports treating "Smile" as an *interactive-report-only* addition rather than a mandatory 12th PDF section — see OI-1 below.

**Conclusion (revised 2026-09-11 — see §4 `FR-022`):** the PDF confirms this project's existing 11-feature, tiered-recommendation, disclaimer-first report *structure* (`FR-009`–`FR-014`, already implemented) does not need to change — same 11 features, same section shape. It does, however, surface one real new requirement the first pass of this document missed: **every one of the 11 feature pages carries its own "BEFORE"/"AFTER" image slot** (see the literal PDF text extraction in the table above — Hair, Eye, Nose, Cheek, Jaw, Lip, Chin, Skin, Neck, and Ear pages all show `BEFORE` / `AFTER` labels; Nose, Jaw, and Chin additionally show `PROFILE` angle labels). This project's Phase 1 report deliberately kept `FR-010`'s "projected potential" **text-only**, with no AI-image generation (`FR-010`'s v1.9 resolution note says so explicitly: *"no AI-image generation exists in Phase 1 (that's Phase 2 scope)"*). The PDF evidence means that text-only decision is now superseded under Milestone 2 — see new `FR-022` in §4. What Milestone 2 adds on top of the existing report structure is therefore: (a) the richer **interactive** `/report` experience (§2.2, Facial Assessments + deeper Features Analysis metrics), (b) **per-feature AI before/after imagery** (`FR-022`, this correction), and (c) the three entirely new post-report sections (§2.3–2.5). `report_assembly_service.py` will need a new field per feature to carry the generated image reference, and `report_pdf_service.py` will need to render it — both are Milestone 2 scope now, not untouched as the original pass of this document concluded.

## 7. Verification Note (2026-09-11) — Why This Document Changed Mid-Stream

The user directly asked whether the video's requirements had been properly considered, and — after an initial reassurance — pushed back with *"properly check ui and functionality both. dont just guess."* That was a fair challenge: the original review sampled the video at a fixed 3-second interval, which is coarse enough to miss content on a screen that a demo only holds for one second, or to catch a screen mid-scroll instead of settled. This section documents what a second, much denser pass actually found, so the correction is traceable rather than silently absorbed into the numbered items above.

**Method used for the re-check:**
- Computed frame-to-frame pixel difference at 0.5s resolution across the *entire* 137s video to map exactly where real content changes happen versus where the screen is static (being read, not transitioning) — this pinpointed the narrow windows worth dense sampling, rather than blanket-resampling all 137 seconds at high resolution.
- Extracted frames at 0.2-0.3s resolution inside every identified transition window and inspected each one directly.
- Extracted and ran speech-to-text (`faster-whisper`, local, no data sent anywhere) on the audio track to check for narration that might carry functional detail frames alone wouldn't — confirmed it's ambient/background music only (low-confidence, silence-hallucinated output), so no narration was missed.

**What this found and fixed (all reflected in §2 and §4 above):**
1. **Healthy Aging cadence — a real error, corrected.** The original pass reported "+5-year increments, presumed to continue to +20" and, based on that, the client chose "match MyFace" as the resolution to `OI-4`. The actual reference has **4 cards at non-uniform steps (current/28 → +3/31 → +5/33 → +10/38)**, confirmed by watching the scroll hold still at the last card before reversing. The client's stated intent — match the reference exactly — is unchanged; only the data describing what "the reference" actually does was wrong, and is now fixed. This also corrected `OI-2`'s generation-volume estimate (24, not 25+).
2. **Symmetry — was marked "not fully captured, assumed pattern"; now confirmed.** It's on-screen for well under a second in the recording (long enough to be missed by 3-second sampling, short enough that a human watching casually could also miss it), but it does exist and has real, specific content — see §2.2.
3. **Face Shape — genuinely not shown anywhere in the recording.** Verified by densely sampling the exact transition where it should appear: the demo clicks Symmetry, then jumps straight to the AI Visuals nav item.
