- **v1.17 (2026-09-10):** Second follow-up to `ASM-010` (v1.15/v1.16) — the user reported that the identity check correctly detected a mismatch but named the **wrong** photo (uploading a different person as the left-side photo produced an error pointing at the right side instead), so retaking the flagged photo never cleared the error since it was never the actual problem. Root cause: `check_photo_set_identity()`'s odd-one-out selection picked the photo with the **largest summed pairwise distance** to the other two, which is sensitive to pose-driven baseline noise — front-to-right and front-to-left distances aren't perfectly symmetric even for the same person, and this could occasionally tip the sum toward the wrong photo. Replaced with the user's own explicit algorithm: a deterministic match-count vote (each photo counts how many of the other two it's within the identity threshold of; the one matching fewest is the odd one out), with `front` treated as a protected reference whenever the vote ties — either because all three photos are mutually inconsistent (front is never flagged in that case) or because a "hub" photo matches both others while they don't match each other. New `_determine_odd_one_out()` helper in `Backend/app/services/photo_validation_service.py`, independently unit-tested against synthetic pairwise distances for both tie cases (not reproducible from the repo's one `different_person.jpg` fixture alone), plus a new real-fixture test for the exact left-side-mismatch scenario reported. - **v1.16 (2026-09-10):** Follow-up to `ASM-010` (v1.15) — the user reported that after retaking the flagged photo, the error appeared stuck / not updating. The retake mechanism itself was correct (verified via a direct reproduction test hitting the real endpoints in sequence); the actual bug was in routing. `lib/onboarding/nextStep.ts`'s `getNextOnboardingStep` — the single shared function every guard/entry-point uses to decide "where does this user belong right now" — only ever checked `photosCompleted` (every angle individually passed BR-005's per-photo checks), never whether the set was cross-photo identity-consistent. A mismatched set is still `photosCompleted: true` by design (the mismatch is a set-level signal, not a per-photo failure), so **any** entry point that computed the next step — logging in, visiting `/dashboard` directly, finishing the questionnaire — routed a mismatched user straight past `/photos` to `/payment`, skipping the one screen that shows and lets them fix it. Reproduced live: a freshly logged-in user with a mismatched set landed on the payment paywall with no indication anything was wrong. Fixed by adding a `photosIdentityConsistent` parameter to `getNextOnboardingStep` and threading the real value through from `photoStore`'s `identityCheck` at all six call sites (`useOnboardingEntryGuard`, `usePhotoUploadGuard`, `usePaymentGuard`, `useQuestionnaireGuard`, `PhotoWizard.tsx`, `QuestionnaireWizard.tsx`). ## 1. Business Context (`BC-*`)

- **BC-001** [Client-stated] The product is an AI-driven facial aesthetics analysis platform, conceptually similar to Qoves.com — an existing real-world service that produces expert, cephalometric-based "aesthetic protocol" reports for clients.
- **BC-002** [Client-stated] The business problem being solved: Qoves-style services depend on human experts manually producing each report, which is slow and expensive. This platform automates that process with computer vision + AI so a similar product can be sold at consumer scale and price point.
- **BC-003** [Client-stated] The commercial model is a paywalled report: a user completes onboarding and photo upload, an AI-generated report is produced, and the user must pay to unlock/view the full report.
- **BC-004** [Client-stated] Project Sponsor: Jay Michaels (paying client). Delivery team: Crest Infosystems (Tejash Patel — PM, Jainesh Bhatt — Business Manager).
- **BC-005** [Client-stated] The client wants to be able to keep extending this codebase with their own team after delivery, using AI-assisted ("vibe coding") development tools — this drives a preference for clean, modular, well-documented code over clever/opaque implementations.
- **BC-006** [Client-stated] The project is explicitly being delivered in phases. Phase 1 is the current, scoped build; several features are deliberately deferred to a later phase (see Section 2 and Section 12).

### 5.3 Required architectural separation
The client has specified this exact layering, and it must be preserved in any derived architecture/technical-design document:

```
UI → Zustand Auth Store → API Client → Backend Auth APIs → JWT/OTP Services
```

(Superseded in v1.2 — the store layer was previously named "Redux Auth Store"; the contract itself — single source of truth, no direct UI-to-API/token access, centralized API client — is unchanged, only the library changed from Redux to Zustand.)

- **UI** — presentational components; no direct API or token access.
- **Zustand Auth Store** — single source of truth for auth state (user, access token, auth status / initializing flag) on the frontend. Refresh token is **not** stored here (`FE-002` v1.4).
- **API Client** — centralized HTTP client that attaches the access token, sends cookies with `credentials: "include"`, and handles proactive refresh + refresh-on-401 (single-flight).
- **Backend Auth APIs** — FastAPI endpoints (Python) for register (email+password → OTP), login (email+password → OTP), OTP verify, refresh, logout, `/auth/me`, and protected-route dependencies for JWT validation. Sets/rotates/clears the httpOnly refresh cookie. (v1.2 had briefly specified Next.js Route Handlers under the since-rejected single-app consolidation; v1.3 reverts this to FastAPI — see change log.) The frontend (Next.js) and backend (FastAPI) are separate applications communicating over HTTP; the frontend calls these endpoints directly from the browser.
- **JWT/OTP Services** — backend-internal services for token issuance/validation and OTP generation/verification (email delivery), decoupled from the route handlers themselves.

## 8. Workflows (`WF-*`)

### WF-001 — End-to-end user journey (Phase 1)
1. Landing page → sign up / log in.
2. Onboarding: 23-question branching questionnaire → BDD/informational-only disclaimer checkbox → submit.
3. Photo Requirements confirmation screen (7-point checklist shown to user).
4. Photo upload (multi-angle) → backend validation (BR-005) → accept or reject with reason.
5. AI processing: MediaPipe/OpenCV landmark & measurement extraction → OpenAI narrative generation using measurements + questionnaire context.
6. Report assembled and auto-published (BR-002).
7. Results page shown with a teaser; full report locked (BR-001).
8. Stripe payment → on success, full report unlocked.
9. Dashboard: report history/status, PDF download, payment history, profile.

### WF-002 — Authentication flow (confirmed, v1.1)
Both **signup** and **login** follow the identical two-step shape:

1. **Step 1 — Email + password.**
   - *Signup:* user submits email + password → backend validates the email isn't already registered, hashes the password, creates a pending/unverified user record.
   - *Login:* user submits email + password → backend validates the credentials against the stored hash.
   - In both cases, on success the backend does **not** yet issue tokens — it proceeds to Step 2.
2. **Step 2 — OTP verification.** Backend generates an OTP, stores it hashed with an expiry (AUTH-011), and emails it to the user (NFR-012). The user submits the OTP.
   - Backend validates the submitted OTP against the stored hash and expiry, and against the attempt/lockout limits in AUTH-011.
   - On success: for signup, the account is marked verified; for login, the session is confirmed. Either way, the backend now issues a JWT access token + refresh token pair (AUTH-002, AUTH-012) and the flow completes as a successful signup or login.
   - On failure: an attempt counter increments; after 5 failed attempts, a 15-minute lockout applies (AUTH-011) before another OTP can be requested.
3. **Authenticated requests:** frontend API client attaches the access token to each request (FE-004); backend validates the JWT on protected routes (AUTH-007).
4. **Token refresh:** when the access token is near expiry (proactive) or an authenticated request returns 401 (reactive), the frontend calls `POST /auth/refresh` with the httpOnly refresh cookie (`credentials: "include"`) → backend validates it against its revocation store (AUTH-010), issues a new access token and rotates the refresh cookie → frontend updates the Zustand auth store transparently (FE-005). Access-token expiry alone must not clear auth or redirect. If the presented refresh token was already rotated out (reuse), the whole token family is revoked and the user must log in again.
5. **Logout:** explicit user action → frontend calls logout → backend revokes the refresh session and clears the cookie (AUTH-010) → frontend clears the Zustand auth store and redirects to login (FE-006). Do not clear auth from unload/visibility/route-change lifecycle hooks.
6. **Invalid refresh session:** if a refresh attempt fails with a confirmed auth error (401: expired, revoked, missing, or reused/rotated-out refresh token), the frontend clears the Zustand auth store and redirects to login (FE-006). Network errors and 5xx must not clear auth.

  **v1.13 revision — the user gave two direct, explicit instructions overriding the above.** (1) *"in welcome back, instead of email while register take name from user"* — `full_name` was added to `DATA-001` (nullable, for pre-existing rows) and made required on `POST /auth/register`; the dashboard greeting and `UserMenu` now use it (falling back to the old email-derived guess only for accounts created before this field existed). - **ASM-010 — Cross-photo identity check: landmark-ratio signature + empirically calibrated threshold (v1.15) — first-pass heuristic, same posture as `ASM-002`.** The user reported that uploading a different person's photo for one required angle was silently accepted — `BR-005`'s recommended check list (exactly one face, frame proportion, occlusion, resolution, brightness) never included a cross-photo "is this the same person" comparison, only per-photo checks. No dedicated face-recognition/embedding model is used (would mean a new, heavier dependency — dlib's `face_recognition`, `deepface`, etc. — not attempted without being asked); instead, `photo_validation_service.compute_face_signature` derives 5 inter-landmark distance ratios (eye/nose/mouth/jaw/face width, all normalized by inter-ocular distance) from the same MediaPipe Face Landmarker `facial_measurement_service.py` already uses, and `check_photo_set_identity` flags whichever of the three uploaded photos has the largest total distance to the other two once all three individually pass their own checks. The 0.6 mismatch threshold was measured, not assumed: computed against this project's own front/right_3q/left_3q fixtures (same person; pairwise distances 0.08–0.33) and a second, genuinely different person's photo (`tests/fixtures/photos/different_person.jpg`, a public-domain US Navy portrait already bundled as ML sample data — different-person pairwise distances 0.71–0.93). Enforced in the UI (`PhotoSetCompleteStep.tsx` blocks Continue and highlights the flagged photo) and independently re-checked server-side at both `POST /payments/checkout` and `POST /analysis` (`PhotoIdentityMismatchError`) so it can't be bypassed by calling either endpoint directly. Not yet validated against a large, diverse real-world photo set — expect a tuning pass, same as every other threshold in `photo_validation_service.py`. see the v1.17 change-log entry above. **v1.18 addendum:** the "all three mutually different" tie-break still picked only one of the two non-front photos (by distance-to-front, a pose-geometry artifact, not an identity signal) — now both non-front photos are returned together, and the API's `odd_one_out: string | null` field is replaced by `mismatched_angles: list[str]` throughout to represent that; see the v1.18 change-log entry above. **v1.19 addendum:** the user supplied a full written spec of the expected stateless-recompute behavior (retake → clear/replace, never blindly preserve a prior error); audited the implementation against it clause by clause and found it already conformant (no code change needed) — see `docs/photo_identity_validation_spec.md` for the full design contract and worked-example table, and the v1.19 change-log entry above for what was added to make that verifiable going forward. **v1.20 addendum:** the v1.19 audit was incomplete — it missed that `usePhotoUploadGuard.ts`'s own auto-redirect effect read the live `identityCheck` value (including its transient post-retake `null` state) as "safe to skip the review screen," which fired a premature redirect to `/payment` on nearly every retake, before the fresh comparison ever came back. Fixed by deciding that redirect once, from the initial page-load fetch only, never from live retake-driven state changes; see the v1.20 change-log entry above and `docs/photo_identity_validation_spec.md` §6 for the full root-cause writeup. **v1.21 addendum:** `PhotoSetCompleteStep.tsx` itself had separately reverted to the pre-v1.18 `odd_one_out` field name (a real `tsc` compile error, silently non-blocking in dev mode) — every per-photo error highlight was broken (all cards rendered green) even though the underlying comparison and message text were correct. Re-fixed, and live-verified end-to-end with three genuinely distinct synthesized identities that the exact "all three different → fix one → fix the other" sequence narrows the flagged set correctly at each step; see the v1.21 change-log entry above.

### Summary
This document is the authoritative, single source of truth for the AI Facial Analysis platform. Phase 1 delivers: a from-scratch build with custom backend-controlled authentication (email + password, then mandatory OTP verification, for both signup and login; forgot-password via a separate OTP-verify-then-set-new-password flow, `AUTH-015`; JWT access + refresh tokens with rotation and reuse detection; **httpOnly refresh cookie** + Zustand-held access token — explicitly not `localStorage`/`sessionStorage`; sessions persist across refresh/tab/browser restart until explicit logout or an invalid refresh session; and a strict UI → Zustand Auth Store → API Client → Backend Auth APIs → JWT/OTP Services layering), a 23-question onboarding flow, enforced photo validation (thresholds to be finalized during development), a MediaPipe/OpenCV + OpenAI facial analysis pipeline, an 11-feature auto-published report with PDF export, Stripe-gated payment, and a basic user dashboard — with app-wide toast feedback (`BR-009`) and confirm-before-destructive-action (`BR-010`) conventions established here and expected to carry into every later module — on **two separate applications**: a Next.js/TypeScript frontend and a Python/FastAPI + SQLAlchemy/Alembic backend, communicating over HTTP, both over a vendor-neutral PostgreSQL database. Admin functionality, the full report review workflow, email notifications, and Meta Pixel/GTM remain deferred to Phase 2 with no client scope change yet. **As of v1.22, AI Visual Features and the AI Beauty Assistant chat are no longer deferred** — the client has supplied concrete reference material for both (plus a third, previously-undocumented enriched-interactive-report item) under the name "Milestone 2"; see `docs/milestone2_requirements.md` and `docs/milestone2_phase_plan.md` for the full spec and implementation roadmap (none of it built yet). **As of v1.23**, three of the five Milestone 2 open items are resolved (`BR-011` — no 12th "Smile" feature, folds into Lips; `BR-012` — PayPal ships visible-but-disabled; the new Facial Assessments scores are confirmed first-pass heuristics) and a fourth requirement, `FR-022` (a per-feature AI before/after image, superseding `FR-010`'s text-only v1.9 resolution), was surfaced. **As of v1.24**, the remaining two items resolved: the image-generation vendor (`ASM-011`, Google Gemini 2.5 Flash Image) and the healthy-aging cadence. **As of v1.25**, a user-requested dense re-verification of the source video corrected the v1.24 aging-cadence data (the reference actually uses a 4-card, non-uniform-step stack, not 5 cards at uniform +5-year steps — see `FR-020`), dropping the confirmed generation volume from 25+ to 24 per report, and confirmed that three sub-sections (Face Shape, Skin, Protocol) are never actually shown in the source video at all — flagged honestly as unconfirmed rather than assumed, see `docs/milestone2_requirements.md` §7. All five Milestone 2 open items remain resolved; only their recorded data changed. As of v1.9, report pricing (`OQ-002`) remains open at the client's explicit request, alongside three delivery-team implementation choices not yet put to the client: the photo-capture angle count (`ASM-005`/`OQ-010`), the AI vendor substitution, DeepSeek instead of the client-stated OpenAI (`ASM-006`/`OQ-011`), and the recommendation-tiering keyword heuristic (`ASM-007`/`OQ-012`). The frontend/backend architecture question (`ASM-004`), refresh-token transport (`OQ-009`), the onboarding-questionnaire content (`FR-003`/`FR-004`, see `docs/onboarding_questionnaire_spec.md`), photo-validation thresholds (`ASM-002`/`OQ-008`), and whether a user can have multiple reports (resolved: no, one per user — `docs/database-design.md` §5) are resolved; hosting remains deferred (not blocking) rather than open.
